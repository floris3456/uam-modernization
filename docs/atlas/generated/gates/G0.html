Proof claim
Deterministic classified fictional evidence, strict contracts, an independent oracle, mutation detection, privacy-canary containment, cleanup, and independently recomputable gate evidence all work together.

Current owner gaps

  • Accountable G0 gate owner and architecture, security, privacy, and test-quality reviewers.
  • Contract authority, fictional test-data steward, independent-oracle reviewer, privacy-canary scanner, build/release evidence, incident response, and repository support accountability.

What are we proving?

Create trustworthy fictional evidence before any live source or production-shaped implementation is allowed.

Why now?

Every later gate needs known inputs, known answers, reproducible failures, and strict contracts. Starting with live Windows or browser behavior would make mistakes harder to see and could expose real data.

What depends on it?

  • Codec-neutral contracts and pure domain or state models.
  • Production-shaped but synthetic endpoint shell work after the rest of the foundation decisions close.
  • T1 fixtures for later Windows, browser, server, portal, lifecycle, and migration proofs.
  • Deterministic fault histories and evidence envelopes consumed by later gates.

Preparation that may happen earlier

  • Read and review the initial ADRs.
  • Draft fictional examples for human review.
  • Keep repository validation and documentation healthy.

Work allowed

  • Review sources, ADRs, terminology, and fictional examples.
  • After the required human decisions: implement versioned strict contracts, fictional T1 models, deterministic generators, an independent oracle, canary scanners, mutation tests, cleanup, and gate-evidence tooling.
  • Use reserved fictional names, fixed clocks, explicit seeds, local schemas, and stable failure codes.
  • Run repository-only experiments that use no VM, live browser profile, production service, real identity, or network data source.

Work prohibited

  • Read a live browser profile or any real activity data.
  • Install or test a Windows service, scheduled task, Coordinator, User Host, or Task Host.
  • Connect to the Windows VM or a server.
  • Create real realm, role, purpose, field, retention, owner, or access mappings.
  • Use production keys, credentials, signing, deployment, support access, or data transfer.
  • Treat fictional success as proof of Windows, browser, database, capacity, restore, security, or operational fitness.

What must humans decide?

  • Name the accountable G0 gate owner and reviewers for architecture, security, privacy, and test quality.
  • Confirm the initial product privacy ceiling as testable fictional transformations.
  • Accept or amend ADR-FS-001 through ADR-FS-005, ADR-FS-030, and ADR-FS-032.
  • Confirm the initial contract vocabulary and decide which open contradictions need experiments before fixture design.

What must be measured with CLI evidence?

  • Two clean-checkout generation runs produce byte-identical canonical packages and matching SHA-256 roots.
  • Strict valid, boundary, invalid, and adversarial contract vectors produce stable bounded results with network access disabled.
  • Architecture checks prove the oracle cannot call production decision code and deterministic code cannot use ambient time or randomness.
  • Mandatory mutations all fail at the expected boundary; no mandatory survivor remains.
  • Every required canary is detected in every declared sink and encoding without leaking the canary value into logs.
  • Classification and lineage are complete, cross-realm and privacy-negative cases fail closed, and temporary artifacts are deleted.
  • A machine-readable evidence manifest binds exact inputs, versions, commands, results, limitations, owners, and cleanup receipts.

What evidence is required?

  • Input, toolchain, schema, fixture, oracle-rule, mutation, canary, scan, cleanup, and generated-package digests.
  • Sanitized reproducible failure bundles with scenario ID, seed, expected result, actual result, and stable error category.
  • An independently recomputable gate record and repository validation report.
  • Named accountable acceptance; `UNASSIGNED` prevents closure.

What causes failure or hold?

Stop on nondeterminism, unclassified or real input, oracle coupling, a mandatory mutation survivor, a mandatory canary miss, an undeletable artifact, evidence that cannot be independently recomputed, or any blocking owner still UNASSIGNED at closure.

Failure, reproduction, cleanup, and recovery

  • Preserve a sanitized failure bundle containing the stable scenario ID, seed, canonical fictional inputs, expected output, actual output, and stable error category.
  • Rerun from a clean workspace and require the same failure. Reject corrupt or unknown fixture versions rather than guessing.
  • Delete every ephemeral generated browser, SQLite, source, scan, and mutation artifact and record cleanup. A cleanup failure is itself a gate stop.
  • Fix the authoritative contract, generator, oracle, or test source; regenerate evidence. Never edit generated evidence to make a test pass.

What does passing unlock?

  • Codec-neutral contracts and pure domain or state models.
  • Production-shaped but synthetic endpoint shell work after the rest of the foundation decisions close.
  • T1 fixtures for later Windows, browser, server, portal, lifecycle, and migration proofs.
  • Deterministic fault histories and evidence envelopes consumed by later gates.

What passing never authorizes

  • Live source access.
  • Real organizational mappings or production policy.
  • Production credentials, signing, deployment, or transfer.
  • A claim that any later platform or operational gate has passed.

Pass condition

All required G0 scenarios and falsification checks pass reproducibly from a clean checkout; required artifacts are classified, independently checked, canary-clean, deletable, and hash-bound; residual risks are recorded; all blocking owners are named; and an accountable human accepts the gate record.
